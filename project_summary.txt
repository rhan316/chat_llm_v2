1. Project Overview

    1.1. Purpose: Spring_AI (repo: chat_llm) is a RAG (Retrieval-Augmented Generation) backend that (a) indexes documentation files and GitHub repository content into a Qdrant vector store, and (b) serves semantic search over that content with cross-encoder reranking. When the vector store yields nothing (or low scores), it falls back to Wikipedia and Stack Overflow, reranks those results too, and merges everything into one ranked list.
    1.2. Tech stack:
        1.2.1. Spring Boot 4.0.7, Java 21 (Containerfile runs on JRE 25).
        1.2.2. Spring AI 2.0.0 (BOM): OpenAI model starter (embeddings), Qdrant vector store starter, Markdown document reader, vector-store advisor.
        1.2.3. spring-boot-starter-web, validation, actuator; JSP-style Bean Validation on records (@NotBlank, @Pattern, cross-field @AssertTrue), jspecify null-marking.
        1.2.4. Infrastructure: Qdrant v1.17.0 via docker-compose (ports 6333/6334); Containerfile exposes 8081.
        1.2.5. Notably absent: Spring Security, JPA/JDBC (commented out), any relational DB, @ControllerAdvice. Despite the artifact name, no chat/generation endpoint exists — only retrieval, reranking and LLM-based query summarization.
    1.3. Architecture pattern: classic layered REST monolith: Controller → Service → (Qdrant VectorStore | external REST APIs). All DTOs are immutable Java records. The only "persistence" is the Qdrant vector store. A Template Method pattern is used for document indexing (AbstractDocumentationIndexer → DocumentationIndexer).

            summarizeQueryForStackOverflow(raw) — extracts 3–8 keywords preserving exact exception/class/method names.
            summarize(...) (private) — POST /chat/completions via aiRestClient; on any error or empty response returns the raw query unchanged (graceful degradation).

    3.5.4. DocSearchService — Type: @Service.
        Responsibility: Plain vector similarity search filtered by technology + technology_version, with topK and similarity threshold validation.
        Note: not referenced by any controller in the provided code (only by the commented-out runner) — effectively dead code / legacy.
        Dependencies: VectorStore.

    3.5.5. RerankedRagService — Type: @Service; the core orchestrator.
        Responsibility: similarity search → rerank → optional external fallback (Wikipedia + Stack Overflow) → merge.
        Constructor builds three dedicated RestClients: OpenRouter (${mentor.rerank.openrouter.base-url}), Wikipedia (15 s read timeout, hardcoded User-Agent with contact email), StackExchange (default base URL, 15 s timeout, GzipDecompressingInterceptor). Fails fast if ${mentor.rerank.openrouter.api-key} is blank. Note: the injected RestClient.Builder parameter is never used — the service constructs its own clients statically.
        Key methods:
            findAndRerankDocuments(query, tech, version, topKInitial, topKReranked[, repository, repositoryRef]) — validates/normalizes; if repository-scoped, wraps execution in GitHubRepositorySyncLock.withReadLock (blocks concurrent re-indexing of that repo/ref).

            fetchWikiSummary(topic) — search title (/w/api.php, srlimit=1) then /api/rest_v1/page/summary/{title}; builds a Document (metadata source=wikipedia); returns null on miss/error.
            fetchStackOverflowAnswer(query) — /2.3/search/advanced (sort=votes, answers≥1, top 5) → picks best question (max score, tie→answer count) → /2.3/questions/{id}/answers (filter=withbody, top 1) → HTML-stripped Document (metadata incl. question id, link, answer score/accepted).

        Dependencies: VectorStore, AiQuerySummarizer, GitHubRepositorySyncLock, @Value properties.

    3.5.6. GzipDecompressingInterceptor — Type: ClientHttpRequestInterceptor (plain class, wired manually into the SO client).

4. Data Flow
4.1. Flow A — Index a documentation file (POST /api/doc/index)

    4.1.1. Client sends multipart form: file + technology + technologyVersion.
    4.1.2. DocumentationController.index — Bean Validation + manual guards; strips values; extracts a path-sanitized display filename.
    4.1.3. AbstractDocumentationIndexer.index — validates extension (txt/md/markdown); sanitizes filename for metadata.
    4.1.4. indexResource (template): DocumentationIndexer.readDocument converts the resource into Documents (Markdown- or TextReader) with base metadata.
    4.1.5. Documents are split on +++RAG_SECTION+++ markers into "section documents" (section indexes recorded), then chunked by TokenTextSplitter (600 tokens).
    4.1.6. Each chunk is re-created with enriched metadata (document_version UUID, chunk_index, chunk_count, indexed_at, tech/version).
    4.1.7. store(): VectorStore.add — Spring AI embeds each chunk via the auto-configured OpenAI embedding model and upserts into Qdrant; then deletes old chunks of the same source/tech/version whose document_version differs (add-then-delete swap).
    4.1.8. Controller returns IndexDocumentationResponse(filename, technology, version, chunks) as JSON.

4.2. Flow B — Index a GitHub repository (POST /api/github/index)

    4.2.1. Client sends JSON GithubIndexRequest; @Valid runs field constraints.
    4.2.2. GitHubController.index → GitHubRepositoryIndexer.index → normalization (name regex, ref hygiene) → write lock on repo+ref (concurrent readers of that scope block; other repos unaffected).
    4.2.3. GitHubClient.resolveRevision — resolve ref → pinned commitSha + treeSha.
    4.2.4. GitHubClient.getRecursiveTree — full tree; 422 if truncated.
    4.2.5. selectFiles — filter blobs by path/extension/size policy; 413 if limits exceeded; empty selection → 422.
    4.2.6. For each selected file: getUtf8TextBlob (skip binary/oversized) → createChunks (section split, token split, GitHub-specific metadata incl. sync_id) → cumulative maxChunks guard → vectorStore.add (embeddings → Qdrant).
    4.2.7. After all files: deletePreviousSyncs removes chunks from earlier syncs of the same repo+ref (atomic-ish swap).
    4.2.8. On mid-run failure after any write: rollbackCurrentSync deletes the partial sync_id, then the exception propagates as a mapped HTTP error.
    4.2.9. Response: GitHubIndexResponse(repository, ref, commitSha, indexedFiles, skippedFiles, chunks); write lock released.

4.3. Flow C — Reranked RAG search (POST /api/rag/search)

    4.3.1. Client sends JSON RagSearchRequest (+ optional repository/repositoryRef query params). Validation enforces top-K bounds and the cross-field rule topKReranked ≤ topKInitial.
    4.3.2. RagController.search strips inputs → RerankedRagService.findAndRerankDocuments(...).
    4.3.3. Scope normalization: if both repo params present → validate formats and acquire the read lock for that repo/ref (so re-indexing can't swap data mid-search).
    4.3.4. Vector search in Qdrant with FilterExpression: always technology + technology_version; scoped adds source_type=github, repository, repository_ref. Top-K = topKInitial.
    4.3.5. Branch — no candidates: scoped → empty list (immediately). Unscoped → fallback: query is LLM-summarized (AiQuerySummarizer) into a Wiki phrase and a StackOverflow keyword set; each source returns ≤1 Document (independent failure isolation); fallback docs are reranked (tryRerankCandidates), sorted desc, limited to topKReranked.
    4.3.6. Branch — candidates exist: rerankCandidates calls OpenRouter /rerank; results mapped back to original Documents (metadata gains vector_score, rerank_score, model/provider; score = relevance score).
    4.3.7. Low-confidence merge: if unscoped and best rerank score < 0.60 (env-configurable), fallback candidates are fetched, reranked, merged, globally sorted, limited.
    4.3.8. Controller maps each Document via ControllerUtils.toHit → RagHit (DTO transformation) → returns RagSearchResponse(query, results) JSON through the standard Spring message converters.

        5.3.1. GitHub flow uses ResponseStatusException → precise statuses (404/413/422/502).
        5.3.2. Everything else throws IllegalArgumentException/IllegalStateException, which without an advice map to generic 500 responses (even for client-caused input errors) — an inconsistency. Validation failures (MethodArgumentNotValidException / constraint violations) get Boot's default 400 handling.
        5.3.3. Resilience patterns: fallback sources fail soft (return null/raw query); indexers use add-then-delete swaps and rollback (GitHub) — but in AbstractDocumentationIndexer.store, a failed delete after a successful add leaves duplicate old+new chunks while the endpoint reports an error.

        5.4.1. Only one interceptor: GzipDecompressingInterceptor on the StackExchange client.
        5.4.2. No AOP, no servlet filters, no MVC interceptors, no @Scheduled jobs.
        5.4.3. spring-boot-starter-actuator is present, but endpoint exposure config is Not determinable from provided context.
        5.4.4. Concurrency control: GitHubRepositorySyncLock (fair RW locks per repo+ref) coordinates indexing vs. repository-scoped searches.

6. Summary

This is a cleanly layered, well-guarded RAG microservice: documentation files and whitelisted GitHub repo content are chunked (section-aware, +++RAG_SECTION+++), enriched with consistent metadata, embedded into Qdrant via Spring AI, and served through a search pipeline that applies metadata-scoped vector retrieval, cross-encoder reranking via OpenRouter, and LLM-assisted Wikipedia/Stack Overflow fallback with score-based merging. Strong points: defensive input validation, path/ref sanitization, add-then-delete versioned swaps with rollback for repo syncs, and a per-repo read/write lock preventing read-during-reindex races. Notable issues: repository-scoped correctness relies on callers supplying matching technology/technologyVersion (they're mandatory even for repo searches), there is no security layer on mutating endpoints, no global exception mapping (non-GitHub errors surface as 500s), and a failed old-chunk deletion in AbstractDocumentationIndexer silently leaves duplicates. Cleanups worth doing: the unused com.openai...VectorStore import, the unused injected RestClient.Builder in RerankedRagService, the wrong "ref cannot be blank" message on the repository field, dead code (DocSearchService, DocumentationIndexRequest, commented DocImportConfig), the dto/stackoverflow vs dto.rag.stackoverflow path/package mismatch, and the hardcoded contact email in the Wikipedia/SO User-Agent.

7. Changes Made During This Session
7.1. GitHub Discussions Indexing

7.1.1. New DTO — GitHubDiscussionResponse

    Type: immutable record in dto/github/client/.
    Fields: number, title, body, List<GitHubComment> comments, Integer answerCount, Reactions reactions.
    Nested records: GitHubComment(String body), Reactions(int totalCount).
    Annotated with @JsonIgnoreProperties(ignoreUnknown = true) to tolerate extra API fields.

7.1.2. GitHubClient — new method getDiscussions(owner, repository)

    Fetches up to 30 recent discussions via GET /repos/{owner}/{repo}/discussions?per_page=30.
    Uses the existing execute(...) wrapper and applyHeaders(...) for consistent auth/error handling.
    Gracefully returns List.of() on 404/422 (discussions disabled for that repo) instead of propagating the exception — a discussion-less repo is not a hard failure.

7.1.3. GitHubRepositoryIndexer.indexLocked — modified flow

    Removed the early 422 throw when selection.files().isEmpty(). This was a critical blocking issue: it prevented discussion-only repositories from being indexed.
    Added indexDiscussions(...) call after the file-indexing loop but before deletePreviousSyncs.
    Changed the final validation from indexedFiles == 0 to indexedFiles == 0 && discussionChunks == 0 (using && not ||). This was a critical bug fix: the original || would have thrown 422 for any repository that had code files but no discussions.

7.1.4. GitHubRepositoryIndexer.indexDiscussions — new private method

    Fetches discussions via gitHubClient.getDiscussions(...).
    Pre-ingestion filtering (Strategy 1): skips any discussion where !isAnswered && upvotes < 2 — prevents unresolved noise from entering Qdrant.
    Volume cap: breaks after 10 indexed discussions to prevent Qdrant overflow in a single sync.
    Concatenates discussion title, body, and all comments into a single text blob using +++RAG_SECTION+++ separators.
    Attaches metadata: source_type=github, document_type=discussion, repository, repository_ref, commit_sha, sync_id, path=discussions/{number}, language=en.
    Expiration timestamp (Strategy 4): adds expires_at = Instant.now().plus(60, DAYS).toEpochMilli() as a numeric epoch-millis metadata field (Qdrant range filters require numeric types, not ISO strings).
    Applies the same TokenTextSplitter configuration (600/250/50/20_000) as the file indexer.
    Respects the cumulative maxChunks guard across both files and discussions.
    Returns the count of added chunks; indexLocked accumulates this into totalChunks and sets currentSyncStored = true if any were added.

7.2. Time-Based Discussion Cleanup

7.2.1. ScheduledDiscussionCleanup — new @Service

    Injects VectorStore.
    @Scheduled(cron = "0 0 3 * * *") — runs nightly at 03:00 if the app is up.
    @EventListener(ApplicationReadyEvent.class) — also runs on startup so that missed nightly cleanups are caught up after a restart or redeploy. This addresses the reality that this app is not a 24/7 always-on service.
    Deletes all documents where source_type == "github" AND document_type == "discussion" AND expires_at < System.currentTimeMillis().
    Failures are caught and logged; cleanup errors do not crash the application.

7.2.2. SpringAiApplication — @EnableScheduling added

    Required for @Scheduled annotations to be processed by Spring's task scheduler.

7.3. Conversational Chat with RAG-over-History (Method 3)

7.3.1. New DTOs in dto/chat/

    ChatRequest(conversationId, query) — validated with @NotBlank, @Size.
    ChatResponse(conversationId, answer).

7.3.2. ChatHistoryService — new @Service

    Saves individual messages to Qdrant with metadata: source_type=chat_history, conversation_id, role, timestamp.
    getRelevantHistory(conversationId, currentQuery, topK) — performs a similaritySearch filtered by source_type=chat_history AND conversation_id={id}. Returns only the semantically relevant past messages for the current query, not the entire raw history.

7.3.3. ChatService — new @Service

    Injects ChatClient.Builder, ChatHistoryService, RerankedRagService, and @Value("${ai.summary.model}") (the cheap qwen3.7-flash model).
    Query rewriting (rewriteQuery): before hitting RAG, sends the recent chat history + the new follow-up question to the cheap LLM with a prompt asking it to rewrite the follow-up as a standalone, self-contained question. This resolves pronouns and context references (e.g., "Can I use it with JOIN?" → "Can I use SQL UNION with JOIN?"). On any error or empty response, falls back to the raw query.
    RAG retrieval: passes the rewritten standalone query to RerankedRagService.findAndRerankDocuments(...). This hits Qdrant first, and triggers Wikipedia/StackOverflow fallback if scores are low — the same pipeline as /api/rag/search.
    Final answer generation: builds a system prompt containing only the retrieved RAG context (not the raw history), then calls the LLM using OpenAiChatOptions.builder().model(cheapChatModel).build() to override the default model and route to the cheap endpoint.
    History persistence: saves both the user query and the assistant's response to ChatHistoryService for future semantic retrieval.
    Snowball prevention: the final LLM prompt never receives the raw conversation history — only the rewritten query and the semantically selected RAG context. This prevents the context window from growing unboundedly as the conversation progresses.

7.3.4. ChatController — new @RestController

    POST /api/chat — accepts @Valid @RequestBody ChatRequest, delegates to ChatService.chat(...), returns ChatResponse.
